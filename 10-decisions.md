# 10 — Decisions

Every product and engineering decision made so far, with rationale and the trade-off accepted.

Status: draft (items marked *settled* are fixed in the PRD)

| # | Decision | Rationale | Trade-off | Status |
| --- | --- | --- | --- | --- |
| 1 | One engine, two presets, two tracks — not two codebases [src: Monad Sealed-Bid Auction Engine.md] | Proves the engine is a primitive; halves contract surface | Second use case is only as good as the shared core | settled |
| 2 | Fair Launch is the primary submission in track 03 Social, Attention & Culture [src: Monad Sealed-Bid Auction Engine.md] | Strong DeFi teams crowd track 01; a rigorous mechanism is an execution outlier in track 03; the sniper demo reads to any judge | Track-fit is a write-up problem; culture judges won't read the clearing loop | settled |
| 3 | Exit-Priority Auction ships as a second submission only if multiple submissions are allowed and use case 1 is done by day 14; otherwise it is a preset [src: Monad Sealed-Bid Auction Engine.md] | Protects the primary; still demonstrates generality | Finance-track prize possibly forfeited | settled, gated |
| 4 | ICO/raise is a preset (Raise), not a submission [src: Monad Sealed-Bid Auction Engine.md] | "ICO platform" reads as 2017; no distinct audience; near-zero marginal work | None material | settled |
| 5 | Fork EasyAuction for clearing [src: Monad Sealed-Bid Auction Engine.md] | Audited marginal-bid logic, partial fills, multi-tx settlement | LGPL-3.0 copyleft; uint96 limits; must read the fork line by line | **superseded by #22** (22 Sep) |
| 6 | Hand-write commit-reveal, slashing, LP seed [src: Monad Sealed-Bid Auction Engine.md] | No reference implementation; money path | Slower; these are the highest-risk lines | settled |
| 7 | Hash preimage is `(price, amount, salt, msg.sender)` [src: Monad Sealed-Bid Auction Engine.md] | Salt defeats brute force; sender defeats replay and reveal front-running | Salt must be kept client-side; lost salt = slash | settled |
| 8 | Uniform capped deposit, not bid-proportional [src: Monad Sealed-Bid Auction Engine.md] | Proportional deposit leaks the bid (a16z) | More idle capital; bid size bounded by the cap | settled |
| 9 | Slash non-revealers [src: Monad Sealed-Bid Auction Engine.md] | Makes reveal refusal costly | Honest users who lose a salt are punished; slash destination TBD | settled (destination open) |
| 10 | Keep a mandatory minimum bid size (on the max spend) [src: Monad Sealed-Bid Auction Engine.md] | Dust commit spam would make the auction unsettleable | Excludes very small bidders | settled |
| 11 | No encrypted mempool dependency; commit-reveal only [src: Monad Sealed-Bid Auction Engine.md] | BTX is a paper with no deployment [src: https://eprint.iacr.org/2026/754]; Cadence says "when fully implemented and released" [src: https://monad.xyz/blog/cadence-multiple-concurrent-proposers]; live docs show plaintext forwarding [src: https://docs.monad.xyz/monad-arch/consensus/local-mempool] | Two transactions instead of one; the user's wish to build on BTX is not met today — logged in [12-open-questions.md](12-open-questions.md) | settled for Oct; revisit |
| 12 | Use BTX as positioning: "when BTX lands, commit-reveal collapses into a single transaction" [src: Monad Sealed-Bid Auction Engine.md] | Honest, forward-compatible, aligns with what Monad is promoting | Requires the sealing layer to be swappable — design it as a module | settled |
| 13 | State the threat model as "the current and next few leaders" [src: Monad Sealed-Bid Auction Engine.md] | Matches the local-mempool docs (N=3 leaders); more credible than overclaiming | Weaker headline than "no MEV" | settled |
| 14 | Claim "snipe-resistant", never "no sniping" [src: Monad Sealed-Bid Auction Engine.md] | Last-reveal and timing leaks exist | Softer pitch | settled |
| 15 | Non-goals: KYC, RWA, FHE/MPC/enclave/ZK, cross-chain, perpetual privacy of losing bids [src: Monad Sealed-Bid Auction Engine.md] | Three-week build | The Alpos et al. ZK approach is out of scope [src: https://arxiv.org/html/2606.14939] | settled |
| 16 | Exit-Priority over liquidation or intent auctions [src: Monad Sealed-Bid Auction Engine.md] | Liquidation auctions get built several times per hackathon; FIFO redemption is where the race is destructive; no incumbent | Heavier vault integration | settled |
| 17 | Curator-mandate auction is the fallback for use case 2 [src: Monad Sealed-Bid Auction Engine.md] | Fits Monad's 10 Aug curator narrative; Morpho live | Weaker demo | settled as fallback |
| 18 | Build on Monad, not Arbitrum | Track fit; nad.fun is the incumbent to contrast; sub-cent fees | Arbitrum has a private sequencer mempool that would make the commit phase more private [src: https://docs.arbitrum.io/how-arbitrum-works/timeboost/gentle-introduction], but CCA + HuddlePad already occupy the launch niche there | draft |
| 19 | Keep contracts chain-agnostic (no Monad-specific precompiles) | Enables an Arbitrum deployment later at no redesign cost | Cannot exploit Monad-only features | draft |
| 20 | Run `/agentguard scan` and publish the report [src: Monad Sealed-Bid Auction Engine.md] | Covers five of the eight bugs; credibility line in the pitch | Not an audit | settled |
| 21 | Demo the head-to-head, not the contract [src: Monad Sealed-Bid Auction Engine.md] | Legible to any judge in twenty seconds | Contract quality still matters for the Grand Champion pick | settled |
| 22 | **Zama-style bids: price per token + token amount.** Winners get their full amount (pro-rata at the clearing price) and pay the clearing price; the overpayment is refunded [src: https://docs.zama.org/auction/how-it-works] [src: user, 22 Sep] | What bidders expect; what Zama and classic uniform-price auctions do; pro-rata ties remove the reveal-order advantage EasyAuction has at the margin (AUDIT.md M6) | **Reverses decision 5.** EasyAuction's clearing loop sums MON budgets, so it cannot produce fixed-quantity fills. Clearing becomes new hand-written money-path code (~one loop plus one pro-rata division); we lose the 2021 audit and need fuzz tests against a reference model | settled 22 Sep |
| 23 | Seed LP on **multiple DEXs** through one adapter interface [src: user, 22 Sep] | Creator chooses venues; one seeder code path | Every adapter is extra money-path code to review. Hackathon scope: Uniswap v3 first (verified Monad addresses [src: https://developers.uniswap.org/docs/protocols/v3/deployments/v3-monad-deployments]), PancakeSwap v3 second (same position-manager interface). Kuru excluded: an order book has no lockable LP position. **Status 25 Sep:** only the Uniswap v3 adapter is built; the engine already splits one pool across several adapters (up to `MAX_SPLITS`), so PancakeSwap v3 is a new adapter, not an engine change. PancakeSwap v3 names its swap callback differently and the GoPlus locker's support for its position manager is unverified, so it is not claimed. | settled |
| 24 | Lock LP with the **GoPlus SafeToken Locker**, `UniV3LPLocker` at `0x24A9eB23De8E6f59BDB981B03E847F0f3ABbFa0d` on Monad [src: https://docs.gopluslabs.io/page/goplus-safetoken-locker] | Address has code on Monad; `lock`, `unlock`, `relock`, `collect` present in bytecode [src: on-chain, Monad RPC, 22 Sep]. Lock is verifiable through GoPlus's locker API | Fee (read on-chain): `DEFAULT` tier takes 0.40% of the position plus 1.60% of collected trading fees; `LVP` 0.64% / 0.80%; `LLP` 0.24% / 2.80%; no MON lock fee [src: on-chain, Monad RPC, 22 Sep] | settled |

| 25 | **Size the LP from the result, not from fixed amounts.** The creator sets `lpShareBps` up front. At the clearing price P, the LP gets `lpShareBps` of the MON raised and `lpShareBps` of the tokens sold | Because MON raised = tokens sold × P, the two sides are automatically in ratio P: nothing is left over except rounding dust. Same idea as Uniswap CCA's pre-committed "share of proceeds" and "reserve tokens" [src: https://developers.uniswap.org/whitepaper_cca.pdf] | Creator must deposit the worst-case reserve (`sellAmount × lpShareBps`) up front; the unused part is a leftover when the round is undersubscribed (Q16) | settled 22 Sep |
| 26 | The **creator** chooses the DEX split per launch [src: user, 22 Sep] | Creator knows their community's venue | More configurations to test; default is 100% Uniswap v3 | settled |
| 27 | Seed the LP **before** any claim, in its own step right after settlement | Proceeds must be spent as one amount, and no auctioned token may exist outside the contract before the pool does (bug #7) | Claims wait one extra transaction | settled |
| 28 | Degen preset: LP is **permanently locked**. The lock owner is the engine, which has no unlock path; the creator is the `collector` and keeps the trading fees | Memecoin norm is burned LP — pump.fun burns it at graduation [src: https://www.barryguard.com/blog/understanding-liquidity-locks]. A permanent lock matches that while keeping fee income and a lock GoPlus's API can verify | Creator can never reclaim the LP. Raise preset: creator-chosen unlock date | settled 22 Sep |
| 29 | **Unsold supply** (and the unused LP reserve) when a round is undersubscribed: **Degen → burned** to `0x…dEaD`; **Raise → returned to the creator** [src: user, 22 Sep] | Burning favours every buyer, whose share of supply rises — right for memecoins. A raise creator needs treasury | Degen creators lose unsold supply; Raise buyers carry the risk of the creator selling later. See the Q16 options table | settled 22 Sep |

| 30 | **Non-revealers' deposits are burned** to `0x000000000000000000000000000000000000dEaD`. One call after the reveal window, `burnUnrevealed(roundId)`, burns `(commits − reveals) × deposit`; O(1) because deposits are uniform. It replaces `slashUnrevealed(bidders[])` and `slashDestination` [decided by Claude at the owner's request, 22 Sep] | Every other destination rewards someone for a missed reveal. **Creator:** could fake demand for free by committing from its own wallets and never revealing, and the commitment count is the one public demand signal [src: Monad Sealed-Bid Auction Engine.md]. **Other bidders:** a leader who also bids would profit from censoring reveals, and leaders are the adversary in our threat model. **Protocol treasury:** we would profit from users' mistakes, which undercuts the fairness pitch. Burning rewards nobody | An honest bidder who loses their bid details loses the deposit to nobody. Mitigated by recovery, #33 | settled 22 Sep |
| 31 | **Exit-Priority runs on our own demo vault**: a minimal ERC-4626 over WMON with an idle buffer and a simulated illiquid strategy. It reuses the same clearing: price = the discount in bps on a tick grid, amount = shares, supply = exit capacity. Capacity per round = `min(idle buffer in shares, maxExitSharesPerRound)`, fixed when the round opens. `openExitRound()` is permissionless once the last round settled and N blocks passed [decided by Claude, 22 Sep] | We cannot change a live protocol's redemption queue, and the PRD scopes it as "one vault, one asset … a simulated run harness" [src: Monad Sealed-Bid Auction Engine.md]. Everyone exiting pays the clearing discount, which stays in the vault and lifts the share price for holders who stay | Not a live integration; a real Monad LST integration is post-hackathon | settled 22 Sep |
| 32 | **Raise preset.** Allowlist = a Merkle root in OpenZeppelin `StandardMerkleTree` format (leaf `keccak256(bytes.concat(keccak256(abi.encode(address))))`); `commit` takes a proof, empty when there is no allowlist. Vesting is in the engine: `tgeBps` paid at claim, the rest linear over `vestDuration` after `cliff`, counted from settlement. Creator-set; UI defaults: 25% at claim, no cliff, 90 days [decided by Claude, 22 Sep] | Standard formats: creators can build the tree with OpenZeppelin's JS library. Per-bidder GoPlus vesting locks would each cost a flat MON fee | More money-path code; Raise is not in the demo, so it is P1 | settled 22 Sep |
| 33 | **Bid recovery from any device.** The UI encrypts `(price, amount, salt)` with a key derived from an EIP-712 wallet signature bound to chain id, engine address and round id, pads it to a fixed size, and passes it as `commit`'s `note`, which is emitted in `Committed` and never stored. Also kept in localStorage and offered as a backup file. The first time a wallet is used, the UI signs twice; if the two signatures differ (some hardware, MPC and smart-contract wallets), on-chain recovery is off for that wallet and the backup file is required before committing [decided by Claude, 22 Sep] | A lost bid now burns the whole deposit (#30), and UX is the PRD's biggest risk [src: Monad Sealed-Bid Auction Engine.md]. With this, a bidder needs only their wallet to reveal | ~100–200 bytes of calldata per commit. Anyone who tricks the user into signing that exact typed message can read the bid early: a privacy leak, not a fund loss | settled 22 Sep |

| 34 | **"One engine" means shared modules, not one contract.** `SealingLayer` + `DepositLedger` + `UniformClearing` are reused by two concrete contracts: `AuctionEngine` (launches) and `ExitAuction` (vault exits). The clearing module is generic: it knows prices, amounts and allocations, not payments [decided by Claude, 22 Sep] | A launch bidder pays MON per token; an exit bidder pays a discount on shares. Keeping payment math out of the clearing lets both reuse it unchanged, which is what proves the engine is a primitive [src: Monad Sealed-Bid Auction Engine.md] | Two deployables instead of one | settled 22 Sep |
| 35 | **No third use case; deepen the fair launch instead.** Add a token factory so a creator can make a fixed-supply token (no owner, no mint, no fees) and launch it from the same page; the creator, not the factory, opens the round [src: user, 25 Sep, "should we add one more use case"] | Judges score per track; the exit auction already proves the engine is a primitive, and a third product would thin both demos. The factory closes the biggest gap with nad.fun (one-click token creation) without touching the money path | One more contract to deploy; tokens are plain ERC20s, so creators wanting tax or custom logic still bring their own | settled |
| 36 | **Passkey accounts with Mera** (Category Labs) as a second way to sign in, next to browser wallets. PRF output → BIP-39 → `m/44'/60'/0'/0/0` → secp256k1 session → viem account behind the same EIP-1193 interface, so no screen changes [src: https://mera.category.xyz/recipes/create-passkey-accounts/; user, 4 Oct] | Community bidders on phones have no extension; Face ID gets them a Monad account in one step, the account is a standard EOA whose phrase imports into MetaMask, and the bid-recovery note still works because local signatures are deterministic | Mera is in preview (0.2.0); libraries load from jsDelivr at pinned versions only when chosen; the key sits in page memory while signed in; needs WebAuthn PRF (iOS 18+, recent Chrome/Android) | settled |
